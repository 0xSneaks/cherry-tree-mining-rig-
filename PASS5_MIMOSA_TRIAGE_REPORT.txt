2. THE THREE MIMOSA FINDINGS AND THEIR CLASSIFICATION

All three were reproduced with the Mimosa CLI (scan <file> --project) and with
the gate itself (git commit --dry-run triggers the identical PreToolUse L3
audit without creating a commit).

FINDING 1 — app/src/proxy.ts:32 [HIGH] "buildCsp 是 code-injection 入口"
Chain: environment variables -> buildCsp() (defined in src/lib/csp.ts).
Classification: FALSE POSITIVE / SAFE BY CONSTRUCTION.

Proof — every fragment of the built CSP string was traced end to end:

  - All env-derived connect-src values (NEXT_PUBLIC_SOLANA_RPC_URL,
    CHERRY_JWKS_URL, CSP_EXTRA_CONNECT_SRC) pass through origin()
    (new URL(url).origin). A serialized WHATWG origin cannot contain CSP
    metacharacters (no whitespace, no ';'), so no CSP directive injection is
    constructible through configuration.
  - The nonce is charset-validated with a fail-closed throw in
    nonceScriptSources (csp.ts): /^[A-Za-z0-9+/_-]+={0,2}$/.
  - `dev` is a boolean that only selects fixed literals.
  - CHERRY_EMBED_ORIGIN is the hardcoded constant 'https://embed.cherry.fun'
    (cherryChat.ts line 22), not environment-derived.
  - No eval or code execution exists anywhere in the flow. The companion
    medium's "代码执行 eval" marker is the dev-only CSP token string
    'unsafe-eval' — a policy directive, not an eval call.
  - Environment variables here are operator deployment configuration, never
    request input; an actor able to set them owns the deployment outright.

FINDING 2 — app/src/lib/server/growthConfig.ts:34 [MEDIUM] cross-file taint
Chain: env (CHERRY_TREE_SEASONS_JSON) -> validateSeasons() ->
"growth/seasons.ts:84 MongoDB 动态排序字段 sort".
Classification: FALSE POSITIVE.

Proof: the flagged .sort calls (seasons.ts lines 73 and 111) are
Array.prototype.sort with fixed inline comparator functions over an in-memory
parsed array. There is no database client anywhere in the app — package.json
contains no mongo/driver dependency. The heuristic matched the text ".sort("
on data with env provenance.

FINDING 3 — app/scripts/ops/runway-report.ts:105 [MEDIUM] cross-file taint
Chain: command-line argument (--history limit) -> refillHistory() ->
"growth/runway.ts:150 MongoDB 动态排序字段 sort".
Classification: FALSE POSITIVE.

Proof: identical pattern — runway.ts line 153 is Array.prototype.sort with a
fixed comparator; the argv value is only a fetch limit for on-chain RPC
events; no database is involved anywhere in this app.


3. ACKNOWLEDGEMENT MECHANISM EXHAUSTION (why the gate could not be cleared)

Every documented Mimosa acknowledgement/remediation path was tested against
the real scanner and the real gate:

  a. Inline "// mimosa-ignore" comments: verified empirically as a real,
     honored mechanism for DIRECT findings (a positive-control fixture is
     suppressed by a same-line comment; --no-ignore-comments restores the
     finding, proving causality). Applied against the chain findings at five
     distinct placements — source line, reported call line, sink signature
     line, and the sink body-marker lines in csp.ts/seasons.ts/runway.ts.
     Result: cross-file chain findings ignore inline suppressions entirely.

  b. .mimosa/security-policy.json (policy init): the policy file IS consumed,
     but only its `command` section demonstrably affects findings — the
     default forbidShell:true actually ADDED a new false high at
     app/src/lib/program/events.ts:188 (a RegExp .exec() misread as shell
     exec). threatModel.exclusions and data.allowedSortFields have no effect
     on chain findings. The policy file was removed afterwards.

  c. Ledger / validate / knowledge: documented as non-verdict-affecting
     (README: history "已展示" does not skip gates; knowledge readback does
     not modify ledger, finding, Hook or verdict; validate is restricted to
     an allowlisted finding contract).

  d. A probe project cloning the exact csp.ts/proxy.ts pair did not
     reproduce the chain in isolation, so no code-level trigger could be
     identified and legitimately neutralized either.

  e. Gate oracle: `git commit --dry-run` triggers the identical gate with
     zero side effects and was used for every verdict check. Final triage
     state: identical block (1 high + 3 medium).

The only remaining ways to clear the gate would have been code changes whose
sole purpose is defeating scanner heuristics (function renames, code motion)
or disabling/weakening the hook — both explicitly prohibited by the work
order. Per instructions, the triage stopped and reported instead.
